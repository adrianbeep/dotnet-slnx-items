## What changed

Sub-task B of parent issue #8: ships `slnx-items remove folder <name>` as the symmetric inverse of `add folder`. Same `<name>` argument shape, same `--solution|-s` option, same resolution logic, same error table — but partitions the result of a cascade walk via `FolderRemoveResult.Cascaded` and prints per-record lines instead of a "Created N" summary.

- New `src/DotnetSlnxItems.Core/FolderRemoveResult.cs`: 2-field `public sealed record(string Path, bool Cascaded)` mirroring `FolderAddResult`. `SolutionItemsService.RemoveFolderAsync` signature changes from `Task` to `Task<IReadOnlyList<FolderRemoveResult>>`. The implementation walks descendants of the normalized path via `Where(f => f.Path.StartsWith(normalized, Ordinal) && f.Path != normalized)` ordered Ordinal, prepends the targeted folder as `Cascaded=false`, calls `_solution.RemoveFolder(folder)` which cascades by design, and returns the records. Pre-absent folders return an empty list (no `FolderNotFound` exception). `PublicAPI.Unshipped.txt` gains the `FolderRemoveResult` block (declaration + `.Path` + `.Cascaded`) and updates the `RemoveFolderAsync` signature line.
- New `src/DotnetSlnxItems.Cli/Commands/RemoveFolderCommand.cs`: `public static class` with `Create()` mirroring `AddFolderCommand.Create()` byte-for-byte — `Argument<string> name` arity 1..1, `Option<string?> --solution|-s`, non-static `SetAction(parseResult => RunAsync(parseResult, name, solution))` (matches the `System.CommandLine 2.0.12` lock-in from #42). Private static `RunAsync` performs CLI pre-flight (rejects `..` and `/`-prefix → stderr + exit 6), resolves the target solution via `SolutionResolver.ResolveFromCwd` (or explicit `--solution`), routes `SolutionItemsService.CreateAsync` and `RemoveFolderAsync` through `ErrorMapper`, partitions on `records.Count == 0` (echoes the user input form, not the normalized path: `Folder 'Build' was not in the solution.`), iterates the records printing `Folder '<record.Path>' removed from the solution.` for top-level and `... removed (cascaded).` for descendants, calls `SaveAsync()`, returns 0.
- `Program.cs` gains 1 line directly below `remove.Subcommands.Add(RemoveFileCommand.Create())`: `remove.Subcommands.Add(RemoveFolderCommand.Create());`. Forward-compatible attach #8a designed for.
- 11 new `[Fact]` scenarios split across two files — 3 in `tests/DotnetSlnxItems.Core.Tests/RemoveFolderAsyncTests.cs` and 8 in `tests/DotnetSlnxItems.Cli.Tests/RemoveFolderCommandTests.cs`. Every CLI test asserts on `run.Result.ExitCode` via `Assert.Equal(...)` per the project's self-review checklist.

## Reviewer notes

1. **Cascade semantics (cite design #1089 §Technical Approach).** The cascade walk catches DESCENDANTS of the targeted folder — `f.Path.StartsWith(normalized, Ordinal)` where `f.Path` is the candidate descendant and `normalized` is the target. `Ordinal` (case-preserving — `.slnx` preserves case) plus trailing-`/` boundary (`/Build/` matches `/Build/docs/` but not `/BuildOther/`). The persistence library's `RemoveFolder(targeted)` cascades by design (removes the targeted folder + every descendant on disk); our service walks the same set in-memory BEFORE the destructive call so the records list can be returned to the caller without losing entries.
2. **Two distinct `.slnf` paths in CLI tests 10 and 11 — both mandatory.** Test 10 (`RemoveFolder_ExplicitSlnfFile_NonZeroExitAndStderrExplains`) exercises Core's `SlnfNotSupported` exception (exit 4) when the user passes an explicit `--solution x.slnf`. Test 11 (`RemoveFolder_NoSolutionInCwd_NonZeroExitAndStderrExplains`) exercises the CLI pre-flight via `SolutionResolver.ResolveFromCwd` returning `null` because `.slnf` is ignored (exit 2 with the CLI-owned "No solution file found in current directory" message). These are different code paths; dropping one would create a coverage hole. Matches the `RemoveFileCommandTests` 7-vs-8 pattern from #42 and the locked decision #1 in proposal #1087. The issue #43 body originally listed "7 [Fact] methods" — typo; this PR fixes it to "8 [Fact] methods" via `docs(issue): fix #43 body test count typo` and the actual code carries all 8 distinct-code-path tests.
3. **Deviation from spec #1088 §Core — `RemoveFolderAsync` cascade walk: spec scenario vs design code.** The spec scenario "Core — `RemoveFolderAsync` returns 3 records for `/a/b/c/` (1 targeted + 2 cascaded)" asserts the records as `/a/b/c/` (Cascaded=false), `/a/b/` (Cascaded=true), `/a/` (Cascaded=true) — i.e., ANCESTORS. The design #1089 §Technical Approach describes (and the implementation uses) a DESCENDANT walk via `f.Path.StartsWith(normalized, Ordinal)`. These two are mutually exclusive under the persistence library's documented behavior: `RemoveFolder(<a/b/c/>)` removes `/a/b/c/` only, leaving `/a/` and `/a/b/` in the solution. The implementation locks the descendant semantic (matches the `AddFolder` ancestor walk's symmetry at the conceptual level — add creates ancestors, remove cascades descendants). The Core test #2 and CLI test #4 pre-create a deeper tree (`/a/b/c/d/` + `/a/b/c/e/` for Core, identical for CLI) so the descendant walk finds real entries. The spec scenario is updated to match in a follow-up; this PR body surfaces the deviation for the reviewer.
4. **Public API surface delta.** `PublicAPI.Unshipped.txt` (Core) gains 3 lines for `FolderRemoveResult` (declaration + `.Path` accessor + `.Cascaded` accessor) and updates the existing `RemoveFolderAsync` signature line to `Task<IReadOnlyList<FolderRemoveResult>>`. Source-incompatible for any external caller of the old `Task`-returning version — `grep` across the repo confirms zero such callers (only `MutationTests` consumers discard the awaited value). PublicApiAnalyzers (3.3.4) is RS0016-silent in this .NET 10 SDK environment per project context #1026; the `PublicAPI.Unshipped.txt` entry is the source of truth for the API surface, not the analyzer's read.
5. **Pre-absent message form (user input vs normalized).** The CLI's pre-absent message echoes the user's input verbatim (`Folder 'Build' was not in the solution.`), not the normalized form (`Folder '/Build/'...`). This matches the `add folder` pre-existing-line idiom (echoes the segment the user typed). The per-record removed lines echo `record.Path` (the normalized form) because that is what the persistence library stored; the asymmetry is intentional.
6. **No `Co-Authored-By:` line.** Conventional commits only: commit 1 `test(core): add RED RemoveFolderAsync cascade scenarios`; commit 2 `feat(core): add FolderRemoveResult record and cascade return for RemoveFolderAsync`; commit 3 `feat(core): walk descendants before RemoveFolder for cascade reporting`; commit 4 `test(cli): add RED remove folder command scenarios`; commit 5 `feat(cli): wire remove folder subcommand to RemoveFolderAsync` (folds Program.cs registration); commit 6 `chore(cli): apply dotnet format whitespace`; commit 7 `docs(pr): draft PR body for feat/#8b-cli-remove-folder`; commit 8 `docs(issue): fix #43 body test count typo`. One extra chore commit compared to the commit plan in design #1089 §Commit Plan — the `docs(issue)` fix is a follow-up that's mandatory per locked decision, so it gets its own commit.
